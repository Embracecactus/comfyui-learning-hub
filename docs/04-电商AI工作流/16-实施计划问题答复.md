# 开源模型实施计划：问题答复

计划原文见本文末尾附录。以下按计划里提出的问题逐条回答，所有数字来自近期实测，任务记录可查（doc13/14/15）。

## 一、H3 能力单元跑通了吗

跑通了，而且比计划要求的形态更进一步。

用个人 API Key 在 RunningHub 跑出第一条云端 H3 视频（352×608、24FPS、5.167 秒），按 doc13 的四项标准验收全部通过：黑色连帽卫衣上身、帽子长袖口袋齐全、`1977` 胸前文字可读、摘墨镜动作时序完整。之后又通过通用接口层复跑一次通过。

计划里要的「固定入参、固定出参、异步化」已经做成了独立的服务，代码在 `scripts/rh_capability_api/`，不绑定 H3 这一个工作流——以后每接一个新工作流，加一份 JSON 清单就行，不用改代码。

入参（对照 wan3.0 的设计，逐项落实）：

| wan3.0 | 我们的接口 | 说明 |
| --- | --- | --- |
| `input.prompt` | `input.prompt` | 提示词 |
| `input.media[]`（reference_image/video） | `input.image` / `input.video` / `input.audio` | 本地路径、HTTP URL、平台文件名三种都收 |
| `parameters.resolution` | `parameters.megapixels` | H3 工作流按百万像素控制 |
| `parameters.ratio` | `parameters.ratio` | 八档枚举，对外用 `9:16` 这类短名，引擎自动翻译成工作流内部的枚举值 |
| `parameters.duration` | `parameters.duration` | 秒 |

出参（`GET /v1/tasks/{task_id}`）：

```json
{
  "task_status": "SUCCEEDED",
  "output": [{"type": "video", "url": "…COS地址…", "local_path": "…已自动转存本地…"}],
  "usage": {"runtime_seconds": "76", "coins": "16"},
  "error": null
}
```

状态机就四种：`PENDING / RUNNING / SUCCEEDED / FAILED`。RunningHub 的十几种错误码在出口处归并成七个稳定枚举（`INVALID_ARGUMENT`、`INSUFFICIENT_BALANCE`、`CONTENT_REJECTED` 等），原始码放在 `error.upstream_code` 里备查——上层不用关心 RunningHub 改不改错误码。

异步化就是 RunningHub 原生形态：提交即返回任务 ID，5 秒一轮查询，任务库落 SQLite，服务重启也能接着查。查询接口是有的（计划里说「没有查询接口也没事儿」，实际上有，还带成本字段）。

有一点和 wan3.0 不同要说明：**RunningHub 会强制重置 seed**，同参数两次运行出两个结果。这不是缺陷，但上层做「确定性复现」时要注意，验收口径要按通过率算（如三跑两过）。

## 二、成本问题：三个选项的真实数字

计划里的问号现在可以填上了。

**RunningHub 工作流 API（实测）**：计费和用什么模型无关，纯按机器运行秒数算，实测四条任务（21s/28s/67s/76s）都是约 0.21 币/秒。关键变量是实例冷热——41GB 的 H3 模型，冷启动加载要 2-4 分钟，也按秒计费。所以：

| 场景 | 单条 5 秒视频成本 |
| --- | --- |
| 实例已热（连续派单） | **14-16 币，约 0.3 元** |
| 冷启动（偶尔跑一条） | 加上加载约 40-60 币，**0.8-1.3 元** |

计划里写的「5-8 元/条」实测不成立，高了一个数量级。20 元钱包跑了几十条还有剩。

**海螺闭源 API**：768P 0.5 元/秒，5 秒视频 2.5 元；2K 0.8 元/秒，5 秒 4 元。它的价值不在便宜，在于效果稳定、参数标准、没有运维。另外实测发现 RunningHub 平台自己也挂了 MiniMax-H3 的标准模型接口（多模态参考生视频），但只对企业级共享 Key 开放，个人 Key 调会报 1014——这条路要企业认证才走得通。

**租 GPU 自部署（3 元/小时档）**：采样本身约 0.1 元/条，加加载摊销 0.3-0.5 元/条，是三者最低。但省的钱要拿去养别的东西：常驻实例、任务队列、监控、故障恢复。H3 每次冷加载 2-5 分钟，弹性伸缩反而放大单位成本，真要跑量得常驻一张卡，一天 72 元起。

**结论**：日均几十条以内，直接用 RunningHub，热实例 0.3 元/条，什么都不用管；日稳定 200 条以上或者要 0.4MP 以上画质，再考虑自己租卡；闭源 API 留着做两件事——质量基线对照、高价值订单兜底。另外 API 扣费走人民币钱包（和平台送的 RH 币/积分是两个钱包，实测签到积分过不了 API 计费闸门），`consumeMoney` 字段恒为空，人民币对账要人工看控制台账单页，这一步还没最终核完。

## 三、对接赢海AI内测，还差什么

计划说「闭环跑通 demo 时开始对接内测」——demo 闭环已经通了，现在就可以开始接。缺口按优先级排：

1. **OSS 转存**：现在产物是自动下载到本地 `artifacts/`，接内测前改成传自家 OSS，对外的 URL 才是长期的（RunningHub 的 COS 地址有时效）。
2. **24FPS 前置转码**：H3 参考视频必须 24FPS，现在靠手工 ffmpeg，要挪进引擎的媒体处理环节，用户传什么帧率都行。
3. **webhook 通知**：现在是轮询，内测量小够用；并发上来之前加上回调，省轮询。
4. **计费对账与限额**：单 Key 有并发上限（421），内测要配排队和每用户限额，免得一个用户把共享实例占满。
5. **失败重试策略**：节点级失败 10 秒内返回且实例保持热，重试很便宜，可以做成自动。

这些全是工程活，没有未知的坑，两三天的工作量。

## 四、变现方式的落地判断

**优先级一：电商企业全案。** 计划分三步走，现在的实测数据正好把第一步的账算清了：

- 第一步（RunningHub 云端小闭环，报价 2000 元）：客户交付物 = 能力单元 API + 若干商品工作流清单 + 内测接入。我们的边际成本：实例热的时候 0.3 元/条，按客户每月跑 500 条算，RunningHub 账单约 150-650 元（看冷热比例），对 2000 元报价毛利率健康。这个价位的客户预期是「能用、稳定、有人管」，不是「便宜」，RunningHub 方案完全撑得住。2000 元里建议含一个月的调优和固定条数的量，超出按量另计。
- 第二步（云端 GPU）：客户量起来后（月千条级）迁移，3 元/小时档常驻，成本降到 0.3-0.5 元/条，多出来的毛利养运维。
- 第三步（客户买卡本地化）：客户数据要留在自己机房时才推。8GB 卡有量化方案（项目里已有 NVFP4/INT8 工作流），24GB 卡体验最好。这步卖的是部署和培训，一次性。

三步用的是同一套能力单元接口，客户侧不用改代码——这是这次把封装层做成「工作流无关」的直接原因。

**课程（小系列）。** 素材已经齐了：docs 里 01-15 篇就是从装环境到云端 API 化的完整踩坑记录，反向梳理就是课程大纲。建议先出 6-8 节的小系列试水：装 ComfyUI、跑第一个文生图、商品图工作流、H3 视频工作流、上 RunningHub、用 API 批量跑。每节配一个能跑通的 JSON。等内测客户的问题反馈进来，再决定要不要做长体系。

## 五、当前风险，如实说

- seed 强制重置：同请求两次结果不同，商品一致性靠提示词约束（目前 `1977` 案例稳定），要更强一致性需要后处理筛选或多跑选优，成本翻倍。
- 失败任务也计运行时长（平台规则），参数迭代要靠失败快速返回的机制压成本，引擎已经这么做了。
- 个人 Key 共享实例：高峰期可能排队或并发受限，内测前观察一周，不行就升企业共享 Key（顺便解锁平台的标准模型接口，包括 H3 闭源版）。
- 计费钱包归属（人民币 vs 币）差最后一步人工对账：看一眼控制台「任务与账单」页今天 5 条记录的扣费明细即可定论。

## 附录：计划原文要点

- H3 能力单元：固定入参（宽高比/分辨率/提示词/参考媒体）、固定出参（视频地址/状态/错误码）、异步化、参考 wan3.0 设计。
- 成本三选项：闭源 API 0.5 元/秒；RunningHub（当时估 5-8 元/条）；租 GPU 3 元/小时。
- 闭环 demo 后对接赢海AI 内测。
- 变现：小白课程（小系列起步）；优先做电商企业全案（云端 RunningHub 小闭环 2000 元 → 云端 GPU → 客户买卡本地化）。
